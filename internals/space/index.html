Bramble.BufferType — Type
BufferType{T,VectorType}

The storage backing a GridSpaceBuffer: a Vector of VectorBuffers indexed by their integer key.

Type parameters

  • T: element type of the vectors (e.g. Float64).
  • VectorType: the vector container (e.g. Vector{Float64}).

Bramble.GridSpaceBuffer — Type
struct GridSpaceBuffer{BT, VT, T}

A pool of reusable VectorBuffers, all of length npts, on a common backend.

Fields

  • buffer: every VectorBuffer in the pool, indexed by its key.

  • free: a stack of keys that are probably free; in_use remains authoritative.

  • backend: the backend the buffers are allocated on.

  • npts: the length of every vector in the pool.

Bramble.SharedBuffer — Type
mutable struct SharedBuffer{BT, VT, T}

A buffer pool that is safe to share between tasks.

A GridSpaceBuffer has a single owner: two tasks borrowing from one concurrently would be handed the same vector. A SharedBuffer instead gives each task its own pool, created the first time that task asks for a buffer.

The pools live in task-local storage, so they follow the task rather than the thread. This matters because a task can migrate between threads at any yield point: keying workspaces on Threads.threadid() looks equivalent and is not, since a buffer borrowed on one thread would then be released into a different thread's pool.

The cost is one pool per task, which is what you want when tasks are long lived — Threads.@threads creates one task per thread, so a 4-thread loop holds 4 pools no matter how many iterations it runs. Spawning one task per work item instead would create one pool per item; prefer spawning per chunk.

Fields

  • backend: the backend each task's pool is allocated on.

  • npts: the length of every vector handed out.

  • nbuffers: how many vectors each task's pool starts with.

Examples

shared = SharedBuffer(backend(), npoints(Ωₕ); nbuffers = 3)

Threads.@threads for i in 1:n
    with_buffer(shared) do tmp
        # `tmp` belongs to this task alone
    end
end

See also: GridSpaceBuffer, with_buffer

Bramble.VectorBuffer — Type
mutable struct VectorBuffer{T, VT<:AbstractVector}

A vector together with a flag recording whether it is currently lent out.

This is a plain wrapper, not an AbstractVector: the pool hands callers the underlying vector via vector, so the buffer itself is never indexed.

Fields

  • vector: the underlying vector that holds the data.

  • in_use: whether the buffer is currently lent out.

Bramble.simple_space_buffer — Method
simple_space_buffer(b::Backend, npts::Int; nbuffers::Int = 3)

Creates a GridSpaceBuffer of npts-element vectors on backend b, pre-allocating nbuffers of them.

nbuffers is a warm start rather than a cap: the right value is the deepest nesting of temporaries you expect, and the pool allocates one more vector the first time it is exceeded.

A pool has a single owner. To share one across tasks, wrap it in a SharedBuffer.

Bramble.unlock! — Method
unlock!(space_buffer::GridSpaceBuffer, i)

Releases the i-th buffer back to the pool.

Releasing a buffer that is already free is a no-op, so a double release cannot put the same key on the free stack twice.

Bramble.vector_buffer — Method
vector_buffer(shared::SharedBuffer)

Borrows a vector from the calling task's pool, returning (vector, key).

Release it with unlock!(shared, key) from the same task; a key is only meaningful to the pool it came from. Prefer with_buffer, which cannot get this wrong.

Bramble.with_buffer — Method
with_buffer(f, space_buffer::GridSpaceBuffer)

Calls f(v) with a vector borrowed from the pool and returns its result, releasing the buffer afterwards even if f throws.

Examples

total = with_buffer(pool) do tmp
    tmp .= 1.0
    sum(tmp)
end
